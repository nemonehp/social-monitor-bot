# Аудит hotfix v1.3.1

## Причины коллизий

1. Allowlist middleware отвечал на любые сообщения в супергруппе, включая служебные сообщения Telegram о создании форумных тем. От имени системного/бот-пользователя они не проходили allowlist, поэтому бот несколько раз писал `Доступ к боту не разрешён`.
2. Интервал был общей транзакцией: если хотя бы одна платформа не проходила capacity guard, новое значение не сохранялось ни для одной платформы.
3. Scheduler одновременно отправлял capacity-alert и отдельный `vk_accounts_zero`/`tg_accounts_zero`, создавая смысловые дубли.
4. Статус показывал только сохранённый старый интервал, а предупреждение — отклонённый новый, поэтому нагрузка отличалась в несколько раз.

## Решение

- Не-private апдейты игнорируются молча, кроме одноразовой команды `/start bind_...`; проверка администратора остаётся в bind-handler.
- Хранится запрошенный интервал, а на каждом scheduler tick строится отдельный `CapacityPlan` для VK и Telegram.
- При дефиците подбирается минимальный безопасный интервал до 86400 секунд; при отсутствии конечного решения платформа ставится на паузу.
- `next_check_at` рассчитывается с platform-specific default interval.
- Legacy zero-account alerts переводятся в inactive без recovery-сообщения.
- Capacity alert остаётся stateful и повторяется раз в 360 минут.
