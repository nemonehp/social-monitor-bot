# Social Monitor Bot

Версия 1.1.0 Telegram-бота для общего мониторинга источников VK и Telegram.

Цель системы — не аналитика и не сложная панель управления, а надёжный сбор и быстрая доставка новых постов и историй в один сигнальный чат.

## Что входит

- Telegram-бот на `aiogram` с минимальным интерфейсом и только inline-кнопками.
- Один общий пул источников для всех разрешённых пользователей.
- Один администратор, заданный через `ADMIN_TELEGRAM_ID`.
- Allowlist пользователей по числовому Telegram ID.
- Добавление одной ссылки или массовый импорт XLSX/CSV/TSV/TXT.
- Поддержка исходной таблицы с отдельными колонками Telegram и VK.
- Редактирование пула: поиск по ID/ссылке/названию, списки по ФО и регионам,
  отдельные алфавитные списки VK и Telegram, пауза, изменение региона, мягкое удаление.
- Глобальная частота проверки.
- Один общий сигнальный чат.
- Telegram-сбор через несколько StringSession-аккаунтов.
- VK-сбор через несколько токенов и только через проверенные российские прокси.
- Проверка прокси: формат, подключение, внешний IP, страна RU и доступность VK.
- Автоматические состояния прокси: healthy, degraded, quarantine, removed.
- Предупреждения администратору о нехватке прокси, аккаунтов и проблемах сигнального чата.
- PostgreSQL-очереди без Redis/RabbitMQ.
- Транзакционный outbox для доставки сигналов.
- Дедупликация постов, историй и Telegram-альбомов.
- Отдельная обработка закреплённых постов VK.
- Дочитывание Telegram-пропусков с `min_id` от старого к новому.
- Перекрывающаяся пагинация VK при длинном пропуске.
- Скачивание только компактных изображений-превью; видео, аудио и документы целиком не скачиваются.
- Сохранение поста даже при неизвестном или повреждённом вложении.
- Автоматическая очистка уже доставленного локального медиа.
- Подготовленная граница `collectors/max.py` для будущего MAX.

## Сетевая схема

Сервер должен находиться вне РФ.

```text
bot                 -> интернет напрямую
worker-tg           -> Telegram напрямую
worker-vk           -> VK только через RU-прокси
delivery            -> Telegram Bot API напрямую
postgres            -> локальная сеть Docker
```

В коде VK нет fallback на прямой маршрут. Если рабочих RU-прокси нет, Telegram и бот продолжают работу, а VK-задачи остаются в очереди.

## Быстрый запуск

### 1. Подготовить сервер

Нужны:

- Linux-сервер вне РФ;
- Docker Engine;
- Docker Compose v2;
- бот, созданный через BotFather;
- числовой Telegram ID администратора.

### 2. Настроить окружение

```bash
cp .env.example .env
python scripts/generate_key.py
```

Полученный ключ вставить в `APP_ENCRYPTION_KEY`.

Обязательно заполнить:

```env
BOT_TOKEN=...
ADMIN_TELEGRAM_ID=...
POSTGRES_PASSWORD=...
DATABASE_URL=postgresql+asyncpg://social_monitor:тот_же_пароль@postgres:5432/social_monitor
APP_ENCRYPTION_KEY=...
```

`APP_ENCRYPTION_KEY` нельзя менять после добавления токенов, сессий и прокси: он нужен для расшифровки секретов в базе.

### 3. Запустить

```bash
docker compose up -d --build
```

Проверить:

```bash
docker compose ps
docker compose logs -f --tail=200
```

Миграции запускаются отдельным одноразовым контейнером `migrate` до запуска рабочих процессов.

## Первый вход

Откройте бота с аккаунта, чей ID указан в `ADMIN_TELEGRAM_ID`, и отправьте `/start`.

Главное меню пользователя:

```text
Добавить источник
Источники
```

У администратора дополнительно:

```text
Управление
```

## Рекомендуемый порядок настройки

1. `Управление -> Прокси VK -> Добавить прокси`.
2. `Управление -> Аккаунты -> Добавить VK-токены`.
3. `Управление -> Аккаунты -> Добавить TG-сессии`.
4. `Управление -> Сигнальный чат -> Подключить чат`.
5. `Управление -> Доступ -> Добавить пользователя`.
6. Добавить одну тестовую ссылку VK и Telegram.
7. Проверить базовую инициализацию и появление новых сигналов.
8. Загрузить основную XLSX-таблицу.

## VK-токены

Поддерживается текст или TXT-файл.

```text
token_1
token_2
```

Либо с понятными названиями:

```text
vk-main;token_1
vk-backup;token_2
```

Каждый токен в одном процессе используется только одним слотом одновременно. Перед каждым запросом действует минимальный интервал.

## Telegram-сессии

Формат совместим с переданным экспортёром: CSV-строка минимум из 10 полей.

```text
username,unused,string_session,api_id,api_hash,device_model,system_version,app_version,system_lang_code,lang_code
```

Можно отправить несколько строк сообщением или CSV/TXT-файлом.

Одна StringSession запускает один последовательный воркер. FloodWait применяется только к конкретной сессии, остальные продолжают работу.

## Прокси VK

Поддерживаются:

```text
http://host:port
http://user:password@host:port
https://user:password@host:port
socks4://host:port
socks5://host:port
socks5://user:password@host:port
host:port
host:port:user:password
user:password@host:port
```

Строки без схемы сначала трактуются как HTTP. Если поставщик отдаёт SOCKS, схему лучше указывать явно.

Прокси попадает в пул только после успешной проверки:

1. разбор формата;
2. сетевое подключение;
3. запрос внешнего IP через сам прокси;
4. страна IP должна быть `RU`;
5. доступность VK API;
6. измерение задержки.

Один случайный timeout не удаляет прокси. После повторных ошибок он последовательно переходит в degraded, quarantine и removed.

`removed` — мягкое удаление из рабочего пула. Запись остаётся в БД для аудита и может быть восстановлена повторным добавлением.

## Массовый импорт источников

Поддерживаются XLSX, CSV, TSV и TXT.

Бот узнаёт следующие названия колонок:

- `Федеральный округ`;
- `Регион`;
- `Ссылка на ТГ-канал РО`;
- `TG ID (для парсера)`;
- `Название TG`;
- `Статус TG`;
- `Ссылка на группу ВК РО`;
- `ВК ID (для парсера)`;
- `Название ВК`;
- `Статус ВК`.

Из одной строки могут быть созданы сразу два источника — Telegram и VK.

Строки со статусом `Не рабочий` или `Отсутствует` пропускаются. Ошибки возвращаются отдельным CSV.

Для больших импортов первая проверка равномерно распределяется по одному интервалу, чтобы не создавать резкий запросный пик.

Шаблон: `examples/sources_template.csv`.

## Как система не теряет посты

Для каждого источника хранятся:

- `monitor_from_at` — момент, с которого источник начал отслеживаться;
- `checkpoint_at` — граница последней полностью успешной проверки;
- platform-specific watermark/cursor для безопасной пагинации.

Первая проверка не импортирует историю. Материалы с датой публикации до
`monitor_from_at` отбрасываются, включая старые закреплённые посты и старые
активные/закреплённые истории. Следующие проверки читают окно после последнего
успешного checkpoint с небольшим overlap; дубликаты отсекаются уникальным ключом.

### Telegram

Для канала хранится последний непрерывно обработанный `message_id`.

При следующем запуске сообщения читаются:

```text
min_id = сохранённый message_id
reverse = true
```

То есть от самого старого пропущенного сообщения к новому. Большой пропуск обрабатывается пакетами, а watermark двигается только до реально записанного места.

Если граница пакета попала внутрь альбома, пакет расширяется до конца этого альбома.

### VK

Сохраняются watermark и последние стабильные ключи.

Закреплённые посты:

- обрабатываются отдельно;
- не сдвигают watermark обычной стены;
- не занимают квоту обычных постов;
- дедуплицируются по `owner_id + post_id`.

Если после долгого простоя старый watermark не найден за один запуск, сохраняется offset. Следующий проход начинается с перекрытием одной страницы, поэтому смещение стены новыми публикациями не создаёт дыру.

### Неизвестные вложения

Сначала сохраняется сам материал:

- стабильный ключ;
- источник;
- дата;
- текст;
- оригинальная ссылка;
- raw-метаданные.

Медиа разбирается отдельно. Ошибка одного вложения не отменяет пост. В худшем случае приходит текст и кнопка оригинала.

## Первая проверка

В момент добавления источника фиксируется UTC-время начала мониторинга. Первый
проход нужен для определения ID, названия и текущих watermark, но сохраняет и
доставляет только публикации, появившиеся после этой отметки. Исторический импорт
постов и историй не выполняется.

## Доставка

Новый элемент и запись доставки создаются в одной транзакции PostgreSQL.

Если процесс упал после сбора, но до Telegram API, доставка останется в очереди.

Если сигнальный чат временно недоступен:

- событие не помечается отправленным;
- выполняются ретраи;
- администратор получает агрегированное предупреждение;
- после восстановления очередь догоняется.

## Формат сигналов

```text
VK · НОВЫЙ ПОСТ

Название источника
Регион · Федеральный округ

Текст публикации

[Открыть оригинал]
```

Для фотографий отправляются уменьшенные версии. Для видео и документов может
отправляться только статичное превью; сам файл не скачивается. Если превью нет,
приходит текстовая карточка и кнопка оригинала.

Telegram-альбом отправляется как media group, но число локально скачиваемых
превью ограничено `MEDIA_MAX_PREVIEWS_PER_ITEM`.

## Частота проверки

В интерфейсе одна глобальная настройка. Значение хранится в секундах.

Стандартные кнопки:

- 1 минута;
- 2 минуты;
- 5 минут;
- 10 минут;
- другое значение.

Минимум задаётся `MIN_POLL_INTERVAL_SECONDS`.

Источники имеют собственный `next_check_at`; система не запускает весь пул одновременно.

## Процессы

```text
bot             интерфейс и административные действия
scheduler       создание задач, восстановление lease, health checks, alerts
worker-vk       сбор VK через RU-прокси
worker-tg       сбор Telegram через StringSession
 delivery       отправка сигналов через Bot API
postgres        состояние, очередь, дедупликация и аудит
```

Очереди забираются через `SELECT ... FOR UPDATE SKIP LOCKED`.

## Резервное копирование

Минимальный backup PostgreSQL:

```bash
docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' > backup.sql
```

Восстановление:

```bash
cat backup.sql | docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" "$POSTGRES_DB"'
```

Также сохраняйте volume `media_data`, если важно удерживать ещё не доставленные файлы историй.

## Обновление с версии 1.0 на checkpoint monitoring

Миграция `0002_checkpoint_monitoring` один раз удаляет старые `items`, `deliveries`
и `collection_jobs`, созданные историческим bootstrap. Источники, регионы,
пользователи, настройки, Telegram-сессии, VK-токены и прокси сохраняются. Момент
применения миграции становится новой границей мониторинга для всех источников.

Перед обновлением обязательно сделать backup PostgreSQL. После остановки сервисов
нужно собрать новую версию, выполнить миграцию и удалить старые локальные медиа из
volume. Пошаговая инструкция: `docs/UPGRADE_V1_1.md`. Автоматизированный вариант:

```bash
CONFIRM_CHECKPOINT_RESET=YES ./scripts/upgrade_checkpoint_v2.sh
```

## Что намеренно не сделано

- веб-панель;
- Redis, RabbitMQ, Kafka;
- Kubernetes;
- индивидуальные интервалы для каждого пользователя;
- несколько администраторов;
- несколько сигнальных чатов;
- аналитика охватов;
- фильтрация по ключевым словам;
- редактирование текста собранного поста;
- поддержка приватных Telegram invite-ссылок;
- MAX-адаптер до получения его механизмов доступа.

## Практические ограничения

- Доступность закрытых данных зависит от прав добавленных аккаунтов.
- VK и Telegram могут менять API и ограничения; ошибки классифицируются и не должны приводить к потере уже полученного события.
- Для VK-видео официальный API часто даёт метаданные и превью, но не прямой файл. В таком случае бот отправляет превью и оригинальную ссылку.
- Один и тот же источник не должен одновременно существовать под разными нормализованными ссылками. Нормализация покрывает основные публичные форматы.
